You are building **Step 8 (Deliverables)** of the Citadel MVP, per
`docs/CITADEL_MVP_DESIGN.md` §6.10. Read that section in full, plus the Artifact/Approval rows of
§4's state-machine mapping table.

## Mission

Close the two biggest gaps the audit found in the full architecture: an artifact that nothing
ever mechanically verifies, and an approval decision that never actually propagated to release
anything. Both get closed here, completely, with no partial states left implicit.

## You own

`app/artifact/` and `app/approval/`.

## Template selection — a no-op

Exactly **one** template exists: `maintenance_summary_v1`. Don't build a template-selection
mechanism; "selection" is a no-op for this slice.

## The Verifier — a plain function, not a service

Called synchronously, right after generation. Not a network call, not an LLM judge:

```python
def verify(artifact) -> bool:
    checks = [
        artifact.file_exists_and_readable(),
        artifact.compute_and_store_sha256(),
        artifact.has_required_sections(["Summary", "Maintenance History", "Sources"]),
        all(e.classification <= task.classification for e in artifact.cited_evidence()),
        len(artifact.provenance) > 0,
    ]
    return all(checks)   # any failure ⇒ task FAILED for this slice, no auto-revision
```

Copy these five checks exactly — do not add an LLM-as-judge step, and do not build an
auto-revision loop for verification failures (that's different from the *approval* rejection
path, which the `orchestrator` agent already scoped to exactly one retry).

## Immutability — enforced at the API layer

```
if artifact.status == "RELEASED": reject()
```

Every mutating endpoint on Artifact must include this check. Document explicitly, in a code
comment, that this is an API-layer control, not a storage-layer write-protection — a true
write-once store is out of scope for this MVP.

## Approval propagation — the one transactional endpoint

This closes the other major gap the audit found: an approval that used to just sit there instead
of actually releasing anything.

```json
// POST /approvals/{approval_id}/decision
// approver_id is derived from the session JWT (built by security-control-plane) — NEVER from
// the request body, no exception.
{"decision": "APPROVED", "comment": "Looks correct."}
```

On `APPROVED`, in **one transaction**:
`Approval.decision = APPROVED`, `Artifact.status = RELEASED`, `Task.status = COMPLETED` — then
emit `APPROVAL_GRANTED` followed by `ARTIFACT_RELEASED` via the single Observability writer.

On `REJECTED`: `Approval.decision = REJECTED`, `Task.status = REVISION_REQUIRED` momentarily,
then hand control back to the `orchestrator` agent's scoped revision logic (§5.3) — you don't
implement the revision yourself, you just trigger the transition and let the Orchestrator's
already-built revision path pick it up.

## State machine mapping you must respect (§4)

| Task | Artifact | Approval | Trigger |
|---|---|---|---|
| RUNNING | TEMP | NOT_REQUIRED | Report generated by agent, not yet checked |
| RUNNING | CANDIDATE | NOT_REQUIRED | Verifier begins checking |
| WAITING_FOR_APPROVAL | VERIFIED | REVIEW_REQUIRED | All 5 verification checks pass |
| WAITING_FOR_APPROVAL | VERIFIED | APPROVED | Approver decision recorded, transaction in flight |
| COMPLETED | RELEASED | APPROVED | Single transaction commits — terminal, happy path |
| RUNNING → FAILED | TEMP (rejected) | NOT_REQUIRED | Verifier check fails → task FAILED |
| RUNNING → REVISION_REQUIRED → RUNNING | — | REJECTED | Approver rejects → one bounded revision |

## Events you must emit

`ARTIFACT_CREATED`, `ARTIFACT_VERIFIED`, `APPROVAL_REQUESTED`, `APPROVAL_GRANTED`,
`APPROVAL_REJECTED`, `ARTIFACT_RELEASED` — all via the single Observability writer, in the order
implied by the mapping table above.

## Explicit non-goals for this component

No LLM-as-judge verification, no multiple templates, no storage-layer write-once enforcement, no
artifact versioning beyond the single `version` field already in the schema.

## Done when

- Full happy path works: generate → verify → approve → release, in one transaction on the final
  step.
- A `RELEASED` artifact rejects any further mutation attempt (test this explicitly, don't just
  assume the check is hit).
- A verification failure marks the task `FAILED` — no silent pass, no partial artifact left in an
  ambiguous state.
- A `REJECTED` decision correctly hands off to the Orchestrator's one-shot revision path rather
  than trying to regenerate the report itself.
