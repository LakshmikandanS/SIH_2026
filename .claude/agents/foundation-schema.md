You are building **Step 3 (Foundation)** of the Citadel MVP, as specified in
`docs/CITADEL_MVP_DESIGN.md` (read §3, §4, and §6.12 in full before writing any code — this file
summarizes them but the design doc is the authority on anything ambiguous).

## Mission

Stand up the six foundation tables and the one module every later component writes events
through. Nothing else in the system can be demoed until this exists, so keep it small, correct,
and exactly matching the schemas below — do not add fields, do not split tables that are
specified as one, do not merge tables that are specified as three.

## You own

`app/db/` (models + migrations/init) and `app/observability/` (the single event writer).

## The three state machines (§4) — never merge these

```
Task:     CREATED → PLANNING → RUNNING → WAITING_FOR_APPROVAL → COMPLETED
                                   ↓
                                 FAILED
          (REVISION_REQUIRED is a transient sub-state of RUNNING, not terminal)

Artifact: TEMP → CANDIDATE → VERIFIED → APPROVED → RELEASED

Approval: NOT_REQUIRED → REVIEW_REQUIRED → APPROVED / REJECTED
```

Encode these as three independent enums/state columns. Do not add a shared "status" table or a
single mega-enum — the mapping between them (which later agents will rely on) is a *join*, not a
merge:

| Task | Artifact | Approval | Trigger |
|---|---|---|---|
| RUNNING | TEMP | NOT_REQUIRED | Report generated by agent, not yet checked |
| RUNNING | CANDIDATE | NOT_REQUIRED | Verifier begins checking |
| WAITING_FOR_APPROVAL | VERIFIED | REVIEW_REQUIRED | All 5 verification checks pass |
| WAITING_FOR_APPROVAL | VERIFIED | APPROVED | Approver decision recorded, transaction in flight |
| COMPLETED | RELEASED | APPROVED | Single transaction commits — terminal, happy path |
| RUNNING → FAILED | TEMP (rejected) | NOT_REQUIRED | Verifier check fails → task FAILED, no auto-revision |
| RUNNING → REVISION_REQUIRED → RUNNING | — | REJECTED | Approver rejects → one bounded revision |

## The single Observability writer (§6.12)

One internal function — a single Python module with a lock around the write path — is the
**only** writer to the Event table for the entire system. It computes
`hash = SHA256(payload + previous_hash)` and appends. This is single-threaded by construction on
purpose: it sidesteps the general concurrent-hash-chain-ordering problem entirely rather than
solving it, because at this scale there's exactly one place total ordering could break.

Event types you must support (every other agent will call your writer with these):
`TASK_CREATED, PLAN_CREATED, AGENT_STARTED, ACTION_REQUESTED, CAPABILITY_CHECKED, POLICY_DECISION,
TOOL_EXECUTED, TOOL_DENIED, EVIDENCE_RETRIEVED, STATE_COMMITTED, ARTIFACT_CREATED,
ARTIFACT_VERIFIED, APPROVAL_REQUESTED, APPROVAL_GRANTED, APPROVAL_REJECTED, ARTIFACT_RELEASED`

Expose one function, something like `append_event(task_id, actor_id, event_type, payload) -> Event`,
and one read function for `/trace` to use later: `get_trace(task_id) -> list[Event]` ordered by
`event_id`/timestamp with the hash chain intact.

## Optimistic versioning (§6.11, relevant to your Task table)

Task status updates need an `expected_version` check: if the caller's expected version doesn't
match the current row, return a conflict rather than overwriting. Since this MVP runs one task at
a time with a single sequential agent loop, you do not need to solve general concurrent-merge —
a mismatch just means "retry the read-modify-write once."

## Explicit non-goals for this component

No retention/purge logic, no backup/restore, no distributed event ordering, no checkpoint/resume
schema. A single demo run keeps everything; a crashed process just leaves the task in its last
recorded status.

## Done when

- All six tables exist and match the schemas above field-for-field.
- The three state machines are independent columns/enums, not one merged status.
- `append_event` is the only code path that writes to the Event table (grep the codebase for
  direct inserts into it — there should be exactly one).
- A quick script can insert a handful of events and confirm the hash chain is unbroken
  (`event.previous_hash == previous_event.hash` for every consecutive pair).
- `get_trace(task_id)` returns events in order with the chain intact — this is what `/trace` will
  call later, so its shape matters to the `cli` agent.
